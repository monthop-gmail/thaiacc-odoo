# ThaiACC 19.0 → 20.0 Migration Contract (v0.1)

Deterministic mapping from the legacy 19.0 Thai accounting stack (the OCA
`l10n-thailand` modules thaiacc shipped on 19.0) to the official Odoo 20
models plus the thin ThaiACC modules. **Fresh installs never touch legacy
data**; this contract applies only to migrated databases.

## Principles

1. Official Odoo 20 models are the target of every mapping — no legacy
   engine is revived (`account.withholding.tax`, `account.withholding.move`,
   the legacy tax-invoice model, `personal.income.tax` all stop existing).
2. Historical accounting stays immutable: posted entries, partners and
   taxes keep their identity; evidence is *mapped*, not re-derived.
3. The mapping is deterministic: same legacy row → same 20.0 vals, always.
   The functions in `l10n_th_migrate/models/mapping.py` are pure and tested
   against recorded legacy-shaped fixtures (`tests/`).
4. Fresh-install path: `thaiacc` installs clean. Migration path:
   `l10n_th_migrate` runs only on databases that contain legacy tables.

## Mapping table

| # | Legacy 19.0 (source) | Odoo 20.0 (target) | Mapping |
|---|---|---|---|
| 1 | `account.withholding.tax` (name, amount > 0, income_tax_form, account) | `account.tax` (`is_withholding_tax=True`, **negative** amount, `l10n_th_income_tax_type`) | `map_withholding_tax()` — rate sign flips; income type from legacy `income_tax_form` (pnd2→service, pnd1→na, else others) |
| 2 | `account.withholding.move` (+ lines) — per-payment WHT evidence | `account.payment.withholding.line` (official engine) | **not reconstructed row-by-row**: official lines are (re)generated by the engine from the mapped taxes and payments; legacy rows are kept as evidence reference only |
| 3 | `personal.income.tax` + `personal.income.tax.rate` | `l10n_th.pit.table` + `l10n_th.pit.rate` | `map_pit_table()` — brackets copied verbatim; the payee's accumulated base is re-derived going forward from official withholding lines |
| 4 | Tax invoice evidence (`tax_invoice_number`, `tax_invoice_date` on the legacy stack) | `l10n_th.tax.invoice` (+ `l10n_th_vendor_tax_invoice_*` fields on vendor bills) | `map_tax_invoice()` — vendor-bill evidence carries the vendor's document number/date verbatim |
| 5 | `res.partner.company_registry` (Thai branch code) | `res.partner.additional_identifiers` scheme `TH_BRANCH_CODE` | `map_branch_identifier()` — zero-padded to 5 digits |
| 6 | `res.company.novat` / partner `novat` (`l10n_th_company_novat`) | **gap — no 20.0 target yet** | blocked on `l10n_th_company_novat` migration (OCA-bridge inventory, MIGRATION-20.0.md §4) |
| 7 | Document sequences with BE-year/quarter legends (`l10n_th_base_sequence`) | same module on 20.0 (kept) | no mapping needed — module carries forward |
| 8 | PND filings (manual reports) | `l10n_th.pnd.report` | regenerate from official withholding lines after taxes/payments are mapped (E20-006) |

## Known gaps

- Gap #6 (`novat`) is the only unmapped piece; it needs the
  `l10n_th_company_novat` 20.0 migration (bridge list in MIGRATION-20.0.md).
- Legacy WHT **certificates** (`l10n_th_account_wht_cert_form`) have no
  official 20.0 equivalent; certificates are read-only history until the
  Later-bucket work decides their successor. Payment evidence itself maps
  via row 2.
- Branch-number legends `%(b1-b5)s` on document sequences
  (`l10n_th_sequence_branch`) read from the removed `company_registry`;
  their 20.0 source will be the `TH_BRANCH_CODE` identifier (row 5) once
  the module migrates.

## Execution order (migration path)

1. Map taxes (row 1) — everything else references them.
2. Map PIT tables (row 3).
3. Payments/entries post through the official engine → withholding lines
   regenerate (row 2). Reconciliation of legacy evidence: match by
   payment + mapped tax.
4. Map tax-invoice evidence (row 4) and branch identifiers (row 5).
5. Generate PND reports (row 8) and verify totals against the legacy
   filings; investigate any delta before closing the migration.
