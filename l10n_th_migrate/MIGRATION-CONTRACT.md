# ThaiACC 19.0 → 20.0 Migration Contract (v0.1)

Deterministic mapping from the legacy 19.0 Thai accounting stack (the OCA
`l10n-thailand` modules thaiacc shipped on 19.0) to the official Odoo 20
models plus the thin ThaiACC modules. **Fresh installs never touch legacy
data**; this contract applies only to migrated databases.

## Principles

1. Official Odoo 20 models are the target of every mapping — no legacy
   engine is revived (`account.withholding.tax`, `account.withholding.move`,
   the legacy tax-invoice model, `personal.income.tax` all stop existing).
2. Historical accounting stays immutable: posted entries, partners and
   taxes keep their identity; evidence is *mapped*, not re-derived.
3. The mapping is deterministic: same legacy row → same 20.0 vals, always.
   The functions in `l10n_th_migrate/models/mapping.py` are pure and tested
   against recorded legacy-shaped fixtures (`tests/`).
4. Fresh-install path: `thaiacc` installs clean. Migration path:
   `l10n_th_migrate` runs only on databases that contain legacy tables.

## Mapping table

| # | Legacy 19.0 (source) | Odoo 20.0 (target) | Mapping |
|---|---|---|---|
| 1 | `account.withholding.tax` (name, amount, income_tax_form, is_pit, account) | `account.tax` (`is_withholding_tax=True`, **negative** amount, `l10n_th_income_tax_type`, `l10n_th_is_pit`) | `map_withholding_tax()` flips the rate and maps form/PIT. The native accounting rehearsal also maps the source WHT posting account to the target tax invoice/refund repartition lines before it posts payments. |
| 2 | `account.withholding.move` (+ lines) — per-payment WHT evidence | `account.payment.withholding.line` (official engine) | **not reconstructed row-by-row**: official lines are (re)generated by the engine from the mapped taxes and payments; legacy rows are kept as evidence reference only |
| 3 | `personal.income.tax` + `personal.income.tax.rate` | `l10n_th.pit.table` + `l10n_th.pit.rate` | `map_pit_table()` — calendar-year key and brackets copied verbatim; the payee's accumulated base is read from official withholding lines. The fixture uses `2026`, as the legacy model's effective date is Gregorian. |
| 4 | Tax invoice evidence (`tax_invoice_number`, `tax_invoice_date` on the legacy stack) | `l10n_th.tax.invoice` (+ `l10n_th_vendor_tax_invoice_*` fields on vendor bills) | On-invoice vendor evidence carries the vendor's document number/date verbatim. CABA payment tax invoices are matched individually by original bill and VAT amount; ambiguous or different amounts remain unresolved, and all source rows are archived. |
| 5 | `res.partner.company_registry` (Thai branch code), `is_company` | `res.partner.additional_identifiers` scheme `TH_BRANCH_CODE`, `l10n_th_pnd_entity_type` | Branch code zero-padded to 5 digits; source person/company status retained for PND because Odoo 20 derives `is_company` from VAT presence. Ambiguous partner matches are reported, never guessed. |
| 6 | `res.company.novat` / partner `novat` (`l10n_th_company_novat`) | **gap — no 20.0 target yet** | blocked on `l10n_th_company_novat` migration (OCA-bridge inventory, MIGRATION-20.0.md §4) |
| 7 | Document sequences with BE-year/quarter legends (`l10n_th_base_sequence`) | same module on 20.0 (kept) | no mapping needed — module carries forward |
| 8 | PND filings (manual reports) | `l10n_th.pnd.report` | regenerate from official withholding lines after taxes/payments are mapped (E20-006); PND1A requires an explicit source designation or manual reclassification, so the fixture does not assert a PND1A total |

The source fixture also includes posted/cancelled ledger rows, customer output
VAT, two progressive PIT payments, partial-payment WHT, bank/PromptPay data,
and legacy 50 Tawi certificates. The runner reports source and target document
control totals separately. It does **not** migrate posted journal lines; the
target accounting must be migrated by the accounting move before this runner's
evidence reconciliation can be a final migration sign-off.

The native Odoo 19 rehearsal in `scripts/rehearse_odoo19.py` imports supported
invoices and reconciled payments into a fresh Odoo 20 database through the
official ORM. It stores source-scoped external IDs, so a repeat run creates no
duplicate canonical moves or payments. It does not cover arbitrary journal
entries, split payments, PIT/PND history, or a missing production snapshot.
See `MIGRATION-GUIDE.md` and `fixture/odoo19_rehearsal_report.json` for the
full ledger deltas and remaining gates.

## Known gaps

- Gap #6 (`novat`) needs the `l10n_th_company_novat` 20.0 migration
  (bridge list in MIGRATION-20.0.md).
- The 2026-09-28 Odoo 19 clone check produced CABA VAT of 2,800 then 7,000
  on a 40%/60% payment of a 107,000 bill. Odoo 20 produced 2,800 then
  4,200. The runner reports the 2,800 delta and leaves the second invoice
  unresolved. This source posting needs investigation before sign-off.
- Legacy WHT **certificates** (`l10n_th_account_wht_cert_form`) have no
  official 20.0 equivalent; certificates are read-only history until the
  Later-bucket work decides their successor. Payment evidence itself maps
  via row 2.
- PromptPay tax-ID and mobile proxies map to official
  `res.partner.bank.proxy_type/proxy_value`; the bank account number alone
  cannot generate an official PromptPay QR.
- Branch-number legends `%(b1-b5)s` on document sequences
  (`l10n_th_sequence_branch`) read from the removed `company_registry`;
  their 20.0 source will be the `TH_BRANCH_CODE` identifier (row 5) once
  the module migrates.

## Execution order (migration path)

1. Map taxes (row 1) — everything else references them.
2. Map PIT tables (row 3).
3. Payments/entries post through the official engine → withholding lines
   regenerate (row 2). Reconciliation of legacy evidence: match by
   payment + mapped tax.
4. Map tax-invoice evidence (row 4) and branch identifiers (row 5).
5. Generate PND reports (row 8) and verify totals against the legacy
   filings; investigate any delta before closing the migration.
