## 2. Trace — what each side recorded

Legacy 19 (per `fixture/odoo19_source_views.sql` →
`legacy19.account_tax_invoice_evidence`): the legacy stack's
`account.move.tax_invoice` records ARE the CABA journal entries
(`is_cash_basis = tax_cash_basis_origin_move_id IS NOT NULL`;
`vat_amount = ABS(ti.balance)`). Row 5 = a posted CABA entry
(Dr 114200 / Cr 114299, VAT 2,800) with a tax_invoice_number + date.

Target 20 (official `l10n_th` engine): CABA entries are generated by
`account.partial.reconcile._create_tax_cash_basis_moves()` for
**on_payment** taxes only, and vendor-side CABA tax invoices are created by
`l10n_th_purchase_tax_invoice`'s hook. The target produced CABA TIs summing
7,000 for the same bill reference; **no CABA pair for the 2,800 slice**.

Matching rule in `_reconcile_caba_tax_invoices()`: legacy row ↔ target TI
matched by **exact absolute VAT amount** per bill reference; unmatched rows
stay unresolved (row 5) and their legacy numbers are NOT written onto
official TIs.

## 4. Decisive queries on the clone (run to pick the classification)

```sql
-- Q1: the full journal of the legacy CABA entry behind row 5
SELECT m.name, m.date, m.state, l.account_code, l.debit, l.credit,
       m.tax_cash_basis_origin_move_id
FROM public.account_move m
JOIN public.account_move_line l ON l.move_id = m.id
WHERE m.id = (SELECT move_id FROM public.account_move_tax_invoice WHERE id = 5);

-- Q2: the source bill's exigibility + partial reconciliation count
SELECT m.ref, m.amount_total, t.tax_exigibility,
       (SELECT COUNT(*) FROM public.account_partial_reconcile apr
        JOIN public.account_move_line dl ON dl.id = apr.debit_move_id
        WHERE dl.move_id = m.id) AS partials
FROM public.account_move m
JOIN public.account_move_line l ON l.move_id = m.id AND l.tax_line_id IS NOT NULL
JOIN public.account_tax t ON t.id = l.tax_line_id
WHERE m.ref = (SELECT bill_reference FROM public.account_move_tax_invoice WHERE id = 5);

-- Q3: the target's CABA TIs for the same bill (on the migrated target DB)
SELECT ti.id, ti.tax_invoice_number, ABS(ti.balance) AS vat,
       ti.tax_cash_basis_origin_move_id
FROM l10n_th_tax_invoice ti
WHERE ti.invoice_move_id = (SELECT id FROM account_move WHERE ref = '…same ref…');
```

- Q1 returning an **isolated balanced pair** with no origin move → legacy
  convention/historical bug.
- Q2 showing `tax_exigibility='on_payment'` + N partials where the target
  produced N−1 CABA pairs → **engine behavior** (split granularity).
- Q3 listing a TI with VAT 2,800 that the matcher missed → **matcher bug**
  (fix the matcher, not the books).

## 5. Decision options for the owner

- **Option A (default, current behavior):** official 20 TIs are canonical;
  legacy row 5's number/date is archived as evidence only. Filings that
  referenced legacy numbers get a cross-reference table.
- **Option B:** nearest-amount mapping (write row 5's number onto the
  closest official TI with a documented approximation flag).
- **Option C:** carry row 5 as a supplementary evidence record attached to
  the bill without touching official TIs.

Any option requires the classification from §4 first — if Q1/Q2 prove a
source historical bug, Option A is mandatory and the bug is reported
upstream to the legacy-stack owners.
